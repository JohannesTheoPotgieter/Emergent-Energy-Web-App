4) LINK-TO-PROJECT BEHAVIOUR (core requirement)
--------------------------------------------------------------------
When Program Manager links a TR item to a project (manual or via confirmed suggestion):

Step 1: Create the link record TRItemProjectLink.
Step 2: Create a High Priority task inside that Project’s task system for the Project Manager assigned to that project.
- Task title: “[TR026] <Action/Description>”
- Priority: High
- Due date: TR due date
- Description: include TR detail summary + deep link back to TR item
- Assignee: project’s assigned Project Manager (infer from project record)
- Tag/Label: “Program Register” (or closest existing tag mechanism)

Store the created task’s ID in TRItemProjectLink.autoCreatedPmTaskId, and update linkStatus accordingly.

Important: NEVER auto-create tasks without explicit user confirmation.
- Suggestions must NOT create any link/task until the user confirms.

Sync rules (minimum):
- If TR due date changes: update all auto-created PM tasks due dates.
- If PM task is marked Completed: mark that TRItemProjectLink linkStatus as Done.
- TR item can only be marked Completed if:
  - all linked project PM tasks are Completed OR there are zero linked projects
  - AND outcomeComments is not empty
  - set dateCompleted automatically on completion

Avoid drift:
- Keep TR as source of truth for RAG and narrative fields.
- Keep PM task as source of truth for execution status.

5) AUTO LINK SUGGESTIONS (new requirement)
--------------------------------------------------------------------
Add “Auto Link Suggestions” that proposes likely projects for a TR item.

Goals:
- Suggest projects quickly and safely.
- Explain WHY each project is suggested (rationale).
- Require review/confirm before linking and task creation.
- Learn from Accept/Reject/Suppress decisions to avoid repeating noise.

Data sources to use for suggestions (infer actual fields by inspecting repo):
- Project name/title
- Project site name (if present)
- Client name (if present)
- Project code/reference (if present)
- Any tags/keywords already stored on projects
- (Optional) historical accepted links for similar TR keywords (lightweight)

Suggestion algorithm (implement without external services unless repo already uses one):
1) Build a TR “search text” blob from:
   - actionDescription
   - department
   - outcomeComments
   - supportingInfo
   - trId
2) Extract candidate keywords:
   - tokenize, lower-case, trim punctuation
   - keep tokens length >= 3
   - remove very common stop-words (a small local list is fine)
   - preserve proper nouns by also extracting TitleCase chunks and acronyms
3) Special parsing for multi-site lines:
   - If outcomeComments contains multiple lines (e.g. TR031), treat each line as a potential project/site keyword.
4) Scoring (simple, explainable):
   - +50 exact substring match between TR text and project name/site/client/code
   - +20 token overlap count (unique tokens) capped
   - +15 if TR contains a known “project anchor token” that matches project (e.g. “Mondi”, “Coega”, “China Town”, “Westway”, “Dipula”, “Shoprite”, “Boundary Terraces”, “Blackheath”, “Paddock”, “Randfontein”, “Tsakane”, “Sibasa”, “Pretoria North”, “Trident”)
   - +10 if any full line (from TR031-style lists) fuzzy-matches project site/name
   - -100 if project already linked to this TR
   - -50 if user previously rejected this suggestion for this TR
   - -999 if user suppressed this project for this TR (do not show)
5) Fuzzy match:
   - Use a lightweight fuzzy approach that matches existing repo conventions (e.g. trigram similarity, Levenshtein, or existing util in codebase).
   - If no fuzzy utility exists, implement a minimal one in a shared util module.
6) Output:
   - Return top N (default 5–8) suggestions sorted by score.
   - For each: project display label + score + rationale bullets (e.g. “Matched token: mondi”, “Matched line: Boundary Terraces”, “Substring match in client name”).
7) UX:
   - “Generate Suggestions” runs server-side (so it can access DB) and returns results.
   - User can:
     - Confirm (creates TRItemProjectLink + PM task)
     - Reject (store decision)
     - Suppress (store decision and hide in future)
   - Provide a “Regenerate” that re-runs scoring and respects decisions.

Safety / guardrails:
- Never link or create tasks automatically.
- Show a confirmation modal summarizing what will happen: “Link TR041 to Project X and create High Priority task assigned to <PM> due <date>”.
- If project has no assigned PM (based on actual schema), block creation and show a required action: “Assign PM to project first” (or use existing assignment workflow).
