PHASE 2 — FIX CORE DATA / BEHAVIOR
Implement the following functional rules:

A. SINGLE SOURCE OF TRUTH
- Tasks and milestones must use one clear and stable underlying model.
- If milestone is a task type, make that explicit and supported everywhere.
- Do not let the UI create phantom rows that are not persisted.
- Every create, update, convert, reorder, and delete must use one consistent service layer.

B. IDEMPOTENT CREATE
- Fix duplicate task creation.
- Ensure one click / one enter / one submit creates exactly one record.
- Prevent duplicate submits caused by:
  - double event firing
  - optimistic UI duplication
  - repeated API calls
  - stale state re-renders
  - enter key + blur both submitting
- Add client-side submit locking and server-side idempotency where appropriate.

C. MILESTONE MODEL
Milestone behavior must be explicit:
- milestone has no duration or duration = 0 depending on architecture
- milestone renders as diamond or equivalent milestone marker on gantt
- milestone has a date and optional finish same as start
- milestone appears immediately in table and gantt after creation
- milestone is sortable and valid in hierarchy
- milestone can be assigned to a parent summary task if applicable

D. CONVERT TASK <-> MILESTONE
Fix conversion behavior:
- converting task to milestone must:
  - validate current task state
  - safely adjust duration/start/finish fields
  - preserve task id unless strong reason not to
  - preserve comments/history/ownership/dependencies where possible
  - update gantt render immediately
  - never fail because of WBS formatting
- converting milestone back to task must:
  - default duration to 1 working day unless specified
  - keep project/location/workstream/owner/status linkage

E. WBS ENGINE
Rebuild WBS handling so it is stable and automatic:
- WBS must auto-generate from hierarchy and order
- WBS must not be manually required for create/convert unless business explicitly needs that
- WBS must update safely when:
  - creating new task
  - inserting task between rows
  - indenting / outdenting
  - converting task to milestone
  - deleting task
  - reordering tasks
- Summary task examples:
  1
  1.1
  1.2
  2
  2.1
- Milestones must be fully compatible with WBS
- No action should fail because WBS is null, stale, or temporarily recalculating
- If needed, separate:
  - hierarchy position logic
  - human-readable WBS display logic

F. TRANSACTION SAFETY
- For complex actions like reorder, convert, indent, outdent, bulk delete:
  - use safe transaction patterns
  - rollback failed state updates
  - show useful error messages
- Never leave the UI in a half-saved ghost state
