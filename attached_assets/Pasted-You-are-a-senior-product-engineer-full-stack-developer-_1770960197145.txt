========================================================
5) STATUS RULES (EXACTLY AS DESCRIBED)
========================================================

A) COS / “Realised vs Not Realised”
1) If task is completed AND PO number exists AND invoice number exists AND invoice raised date exists (and is “black/actual”)
   => COS Realised

2) If task is completed AND PO number exists AND invoice number exists BUT invoice raised date is “red/planned”
   => Not yet COS realised (it’s expected, but not realised)

3) If task is completed AND PO number exists BUT invoice number is empty AND invoice raised date is “red/planned”
   => Not yet COS realised
   => Invoice raised date is being tracked as a monthly placeholder (we track the exact date inside that month)

B) Cashflow / Payment logic (Finance Payment Date)
This is the rule for whether the Finance Payment Date represents planned vs already paid:
1) If Finance Payment Date is “red/planned” AND invoice number exists
   => Planned payment (not paid yet)

2) If Finance Payment Date is “red/planned” AND invoice number is empty
   => Planned payment (not paid yet)

3) If invoice number exists AND Finance Payment Date is “black/actual”
   => Paid already

If any of the “red/black” concept is not stored in the DB today, implement it as:
- payment_date_type ENUM('planned','actual')
- invoice_raised_date_type ENUM('planned','actual')
(or derive “actual” if there is an actual payment event captured elsewhere; if unclear, ask)
