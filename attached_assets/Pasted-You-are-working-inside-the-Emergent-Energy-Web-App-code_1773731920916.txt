You are working inside the Emergent Energy Web App codebase.

Your job is to take the application to a production-ready state by:
1. completing full functionality across all existing views, subviews, tabs, modals, drawers, buttons, tables, cards, forms, KPIs, workflows, and navigation paths
2. fixing broken, empty, inconsistent, missing, or partially wired functionality
3. improving UX, visual quality, flow, clarity, and consistency
4. preserving and building on the existing app, data, imports, and new database structure
5. not breaking current working functionality, not losing data, and not changing the operational source of truth logic

This is not a greenfield rebuild.
This is a controlled production hardening and functional completion exercise.

==================================================
CORE NON-NEGOTIABLE RULES
==================================================

1. DO NOT BREAK EXISTING WORKING FUNCTIONALITY
- Do not remove working routes, tables, actions, forms, KPIs, or workflows.
- Do not rename fields, routes, API contracts, or database structures unless absolutely necessary.
- If a rename or refactor is required, implement a backward-compatible compatibility layer.
- Preserve current data and current behavior where already correct.

2. SOURCE OF TRUTH RULE
- The app must work from:
  a) the imported / front-end maintained data
  b) the new database structure
- Treat this imported operational data + maintained DB structure as the source of truth.
- Do not introduce shadow logic, parallel truth tables, or duplicate derived logic in random components.
- UI must read from stable selectors/adapters/services, not from scattered business logic inside views.
- Any derived KPI or summary must trace back clearly to the source tables / imported maintained data and the new DB structure.

3. NON-DESTRUCTIVE IMPLEMENTATION
- No destructive migrations.
- No deletion of existing production data.
- No breaking changes to existing records.
- If schema evolution is needed, create additive migrations only.
- If legacy fields are still used, preserve them until safely migrated and mapped.

4. NO FAKE COMPLETION
- Do not leave dead buttons, placeholder clicks, fake success states, empty stubs, unhandled loaders, or mock-only code in production paths.
- Every visible action must either work fully or be intentionally hidden based on role/config.
- Every page must have proper loading, empty, success, warning, and error states.

5. ROLE AND ASSIGNMENT DISCIPLINE
- All assignable work items across the app must support proper assignment.
- Assignment must support:
  a) internal users
  b) external counterparties
- Assignment must use database IDs, not free-text names.
- The app must clearly distinguish assignee type (internal user vs counterparty) and persist this correctly.
- Ensure all assignment dropdowns / pickers populate correctly everywhere in the application.

6. KPI INTEGRITY
- All KPI cards, summaries, and dashboards must reconcile with the underlying operational data.
- KPI logic must align with the revenue trackers, COS trackers, and maintained imported data.
- No KPI may show values that do not reconcile to its source logic.
- If old legacy KPI boards exist, restore the useful business-critical KPI parity where relevant, but calculate from the current maintained data / new DB structure.

7. AUDITABILITY
- Important actions must be traceable.
- Action logs should show meaningful source detail, not only generic status changes.
- Users must be able to understand what changed, from what, to what, by whom, and when where relevant.

8. PRODUCTION READINESS
- Improve performance, clarity, consistency, error handling, and visual polish.
- Ensure production-safe navigation, data fetch logic, and resilient UI behavior.
- Fix broken routes, null crashes, unhandled promises, invalid state transitions, and empty screens.
- No silent failures.

==================================================

Create a complete inventory of:
- all routes
- all screens
- all subviews
- all tabs
- all drawers/modals
- all tables
- all forms
- all visible buttons/actions
- all KPI cards and summaries
- all permission-sensitive areas
- all assignment controls
- all related API calls
- all data stores/hooks/selectors/services

- all import pipelines / source adapters

Then identify for every screen:

- what data it reads
- what data it writes
- what actions exist
- what is currently broken
- what is partially implemented
- what is visually weak or confusing
- what has inconsistent UX compared to the rest of the app

Do not guess. Inspect the actual codebase and actual structures first.
