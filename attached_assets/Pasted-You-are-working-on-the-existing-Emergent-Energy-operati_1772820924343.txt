THE 7 PLATFORM UPGRADES TO IMPLEMENT

⸻

	1.	CANONICAL TASK ENGINE

⸻

Implement a single canonical task model and rules layer.

Requirements:
	•	all task types must resolve to one shared task contract
	•	task types include at minimum:
	•	personal task
	•	engineering task
	•	plan task
	•	quality task
	•	standardize task fields where possible:
	•	task_id
	•	project_id
	•	task_type
	•	title
	•	description
	•	status
	•	owner
	•	assignee
	•	viewer
	•	reviewer if supported
	•	due_date
	•	workstream
	•	priority
	•	created_by
	•	updated_by
	•	timestamps

Implement one canonical status model for all tasks:
	•	TODO
	•	IN_PROGRESS
	•	BLOCKED
	•	REVIEW
	•	COMPLETE
	•	CANCELLED

If legacy values exist such as:
	•	Done
	•	COMPLETE
	•	done
	•	closed
	•	finished

map them cleanly to the canonical model.

Requirements:
	•	all task views must use the canonical status values
	•	all filters must use the canonical status values
	•	reporting must use the canonical status values
	•	task type switching must preserve valid data and not corrupt records
	•	field visibility may vary by type, but data model must remain coherent

Do not leave inconsistent status logic scattered across screens.

⸻

	2.	ADMIN RECOVERY CENTER

⸻

Create an Admin Recovery Center in the front end.

Purpose:
Admins must be able to correct normal operational mistakes through the UI without backend intervention.

At minimum support admin correction for:
	•	wrong project linkage
	•	wrong task type
	•	wrong assignee
	•	wrong viewer
	•	wrong due date
	•	wrong status
	•	wrong workstream
	•	duplicate task
	•	bad import-created record
	•	failed import rerun
	•	wrong project field values
	•	wrong financial mapping input if possible through existing model
	•	orphaned task visibility issues where recoverable through UI

Requirements:
	•	all actions must be permission-restricted to admins
	•	all admin changes must be logged
	•	dangerous actions must show clear confirmation messages
	•	admin actions must fail gracefully
	•	no silent destructive actions

If some recovery actions are not possible due to missing architecture, implement as much as safely possible and clearly document the gaps.

⸻

	3.	KPI TRACEABILITY AND TRUST REPORTING

⸻

Implement KPI traceability inside the app where practical, and in code/documentation where needed.

For each key KPI, make it possible to trace:
	•	KPI name
	•	source table(s)
	•	source fields
	•	transformation logic
	•	API endpoint
	•	page/widget consuming the KPI
	•	last refresh or calculation timestamp if applicable

At minimum support traceability for:
	•	Revenue
	•	COS
	•	GP
	•	Cashflow
	•	Project Progress
	•	Engineering Progress
	•	Quality Status
	•	My Work counts
	•	Portfolio headline totals if available

Requirements:
	•	expose a clear admin-only view or debug/trace panel where safe
	•	where UI exposure is not appropriate, document exact code paths and services
	•	remove ambiguity around “where this number comes from”
	•	flag any KPI that cannot yet be fully traced

Do not fake trust. Build traceability.

⸻

	4.	SMART IMPORT CONTROL TOWER

⸻

Upgrade Smart Import into an observable and recoverable operational subsystem.

Requirements:
	•	visible import history
	•	import run status
	•	file name
	•	uploaded by
	•	upload timestamp
	•	import type
	•	records attempted
	•	records succeeded
	•	records failed
	•	row-level errors where possible
	•	retry or re-run support for admins where safe
	•	clear validation errors
	•	proper HTTP/status handling:
	•	validation issues should not return generic 500 errors
	•	graceful handling of:
	•	missing columns
	•	bad headers
	•	blank required values
	•	duplicate rows
	•	invalid project references
	•	partial valid / partial invalid rows

At minimum the control tower must improve imports affecting:
	•	project-related imports
	•	planning task imports to work_items path
	•	cost imports to normalized_cost_lines
	•	revenue imports to normalized_revenue_lines

Requirements:
	•	no silent corruption
	•	clear user feedback
	•	admin recovery path where possible
	•	downstream reporting impact should be predictable

⸻

	5.	ROLE-BASED COMMAND CENTERS

⸻

Refine the app so each key role has a focused operating command center.

At minimum support useful views for:
	•	COO / Admin
	•	Project Developer
	•	Engineer
	•	Project Manager
	•	Quality Manager
	•	Program Manager
	•	Program Finance Manager

Each role-based view should prioritize:
	•	what needs my attention
	•	my tasks
	•	my blockers
	•	my overdue items
	•	key linked projects
	•	relevant handovers
	•	critical metrics for that role

Requirements:
	•	reduce noise
	•	remove duplicate pathways
	•	make ownership obvious
	•	preserve role permissions
	•	support trust in the front end as the primary work surface

Do not create decorative dashboards. Create operational work surfaces.

⸻

	6.	WORKFLOW GATES AND HANDOVER CONTROL

⸻

Implement clearer workflow gates and baton-pass controls across departments.

At minimum support explicit handover checkpoints for flows such as:
	•	Project Development to Engineering
	•	Engineering to Project Management / Planning
	•	Project Management to Quality where relevant
	•	project execution to closeout where relevant

Requirements:
	•	visible handover status
	•	required fields/checks before gate completion where safe
	•	clear next owner
	•	clear current owner
	•	no ambiguous “in limbo” state
	•	gate history or audit markers where practical

This should align with the project-centric system spine.
The system must make handovers clearer and reduce dropped baton risk.

⸻

	7.	AUDIT, CHANGE, AND DATA GOVERNANCE LAYER

⸻

Strengthen trust by implementing a lightweight but real governance layer.

Requirements:
	•	log important admin corrections
	•	log task reassignment changes
	•	log task type changes
	•	log status changes where practical
	•	log import runs and outcomes
	•	show who changed what and when where feasible
	•	record source of major changes if possible

Also strengthen data governance rules:
	•	identify critical missing fields that undermine reporting trust
	•	enforce required fields where appropriate and safe
	•	improve validation messages
	•	reduce inconsistent free-text values where canonical enums should exist

Do not overbuild.
Implement a practical governance layer that improves reliability and traceability.
