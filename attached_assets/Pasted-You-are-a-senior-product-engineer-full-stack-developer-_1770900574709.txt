3) BUSINESS LOGIC (NO ASSUMPTIONS)
========================================================

A) Status logic for each milestone row (must be visible in UI)
Using ONLY the rules provided:

1) Planned only (NOT realised)
- payment_received_date is empty
=> show as Planned (and the UI indicator equivalent of “red date”)

2) Issue
- payment_received_date exists BUT invoice_number is empty
=> Flag: “Receipt date exists but invoice number missing” (this is the “black without invoice number” issue)

3) Settled / In bank
- payment_received_date exists AND invoice_number exists
=> Status: Settled
=> in_bank should default to TRUE (unless you find an existing “in bank” field; if it exists, respect it)

If any of the above conflicts with existing app semantics (“Received” vs “In bank”), pause and list the conflict as a question before changing logic.

B) High-level totals (cards/summary)
Compute:
- Total Contract = sum(milestone_value)
- Invoiced = sum(milestone_value where invoice_number exists)
- Received = sum(milestone_value where payment_received_date exists)
- In Bank = sum(milestone_value where in_bank = true)
- Pending = sum(milestone_value where payment_received_date is empty)

C) High-level COSTED vs ACTUAL table
- Planned Revenue (COSTED) = Total Contract
- Planned Expenditure (COSTED) = from project costed/budget value (if it exists in current data model)
- Planned Profit (COSTED) = Planned Revenue - Planned Expenditure
- Planned Margin (COSTED) = Planned Profit / Planned Revenue

- Actual Revenue (ACTUAL) = sum of milestones where payment_received_date exists (or in_bank true, if your finance definition uses banked only — if unclear, ask)
- Actual Expenditure (ACTUAL) = from actual costs already captured in expenditure tables for this project (existing app source)
- Actual Profit/Margin computed accordingly

VO PM LIMIT and CURRENT VO Total:
- Use existing app values if already implemented.
- If not present, add placeholders and list the missing source as a question.
