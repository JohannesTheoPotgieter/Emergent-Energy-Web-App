Use the current repo as the source of truth and redesign /pd into an operational Project Development dashboard.

First inspect before changing:
- client/src/pages/pd-dashboard.tsx
- server/departments/opportunities-routes.ts
- server/routes/project-development-workspace-rollup.routes.ts
- client/src/config/app-navigation.ts
- client/src/config/navigation-permissions.ts
- role/page registry and permission matrix files tied to /pd, /opportunities, /clients, /handover-control

Objective:
Turn /pd from a CRM-style summary into a control tower for PD execution, handover readiness, and cross-company interaction.

Non-negotiables:
- No fake or inferred metrics. Hide weak data.
- No dead-end cards. Every interactive tile must drill into a real filtered view.
- No duplicate logic if an existing endpoint already provides the data.
- No permission drift between nav, page access, and API access.
- Do not break /opportunities, /clients, /handover-control, existing filters, or role access.

Design principles:
- Put operational action first, commercial summary second.
- Prioritize exception-based design: overdue, blocked, stale, unlinked, handover-ready.
- Show owner, status, blocker, age, next action.
- Make “what needs action now” obvious in <5 seconds.
- Use progressive disclosure: top summary → actionable queues → context.
- Show source and freshness for each major section.
- Empty states must be useful, not blank.

Required sections:
1. Top strip: Active eligible opportunities, overdue follow-ups, blocked by internal dependency, handover-ready, linkage/data gaps, stale opportunities.
2. PD Operating Board: grouped by operational progression, not vanity stages.
3. Cross-company interaction: engineering dependency, finance/internal linkage blockers, workspace rollup gaps, broken handovers.
4. Ownership view: by PD owner with active count, overdue count, stale count, due-this-week, handover-ready count.
5. Action queue: prioritized list of items needing action now.
6. Commercial context: weighted pipeline, recent wins/losses, moved lower.

Implementation rules:
- Reuse /api/pd/dashboard only if it remains clean; otherwise create a new read-model endpoint.
- Prefer server-side aggregation over client-side stitched logic.
- Keep metric definitions deterministic and document them.
- Add query params for drilldown routing only where needed.
- If a card cannot reconcile to a filtered list, remove or redesign it.

QA gates:
- counts reconcile to source list
- drilldowns match visible numbers
- role-based visibility works
- API and UI permission keys align
- no runtime errors
- no misleading placeholders
- all timestamps render correctly
- mobile/tablet layout does not regress

Deliverables:
1. current-state audit
2. proposed information architecture
3. metric definition table
4. implementation
5. QA report with reconciliations, risks, and anything hidden due to weak trust
